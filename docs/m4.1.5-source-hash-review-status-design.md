# M4.1.5 — `Unit.source_hash` + `Unit.review_status` design

**Status:** architect pass, pre-implementation. Slice between M4.1 (merged)
and M4.2 (Tauri command surface refactor). Touches `crates/core` (adds
two `Unit` fields), `crates/adapter-qt` (populates `source_hash` on
extract), and `crates/project` (owns the review-status store).

This doc is the contract. It does not re-litigate M4.1; see
[`m4.1-project-crate-design.md`](m4.1-project-crate-design.md) for the
project crate's existing shape (manifest, `ProjectFs`, `ProjectPaths`,
`CorrectionStore`, error model). The originating user intent lives in
[`feedback-2026-05-24-chatgpt.md`](feedback-2026-05-24-chatgpt.md) §§1–2.
Milestone scope is [`roadmap-product.md`](roadmap-product.md) §M4.1.5.

The two invariants from `CLAUDE.md` constrain the design:

1. The Qt `.ts` round-trip is byte-stable. **Review status is never
   written into a `.ts` file.** It lives in gitignored project state.
2. Deterministic Rust does everything except text generation. The
   `source_hash` is a pure function of catalog content; the invalidation
   rule is a pure function of `(stored_hash, current_hash)`.

## 1. The two `Unit` field additions

```rust
// crates/core/src/unit.rs — additions to `Unit`

/// Short content-addressed digest of the *translator-visible* identity of
/// the source for this unit. Populated by the adapter on extract; `None`
/// when the adapter does not (yet) compute one (PO and ICU-JSON
/// adapters in early M4 ship `None` and start filling it in later
/// milestones without a `Unit` schema bump).
///
/// Format: `"sha256:<12 hex chars>"` — the first 48 bits of a SHA-256
/// over the components defined in §2 of the M4.1.5 design.
///
/// # What this guarantees
///
/// - Stable across repeated extracts of the *same* on-disk bytes for
///   the same unit.
/// - Changes when the source text, the disambiguation comment, or the
///   developer comment changes.
///
/// # What this explicitly does NOT guarantee
///
/// - Collision resistance at cryptographic strength. The hash is
///   truncated to 48 bits; this is enough for one project's corpus
///   (~10k units), not enough for cross-project comparison. The hash
///   exists to detect "the source I approved against has changed," not
///   to identify a unit globally (that is what [`UnitId`] is for).
/// - That a missing `source_hash` (`None`) implies the unit is new.
///   `None` means the adapter that produced this unit did not compute
///   one; older adapters and tests construct units with `None`.
#[serde(default, skip_serializing_if = "Option::is_none")]
pub source_hash: Option<String>,

/// Translator-facing review state, **orthogonal to [`UnitState`]**.
///
/// Where [`UnitState`] mirrors the catalog's structural state (Qt's
/// `<translation type="...">` vocabulary), `review_status` records the
/// reviewer's process state — has someone confirmed this MT proposal,
/// has it been locked against further machine edits, is it disputed.
///
/// `None` is the canonical default for a freshly-extracted unit: the
/// adapter does not synthesize a status, the project crate fills it in
/// from `<state_dir>/review.jsonl` on load (§5), and the UI promotes
/// `None` to `New` only as a *display* convention — the persisted shape
/// stays `None` until something happens to the unit.
///
/// **Never serialized into the catalog file.** Review status lives in
/// gitignored project state.
#[serde(default, skip_serializing_if = "Option::is_none")]
pub review_status: Option<ReviewStatus>,
```

A third field (§6 invalidation rule) lands alongside these two:

```rust
/// True when this unit's `review_status` was recorded against an
/// earlier `source_hash` that no longer matches the current extract.
///
/// Derived at project-open time by comparing `source_hash` against the
/// hash stored in `review.jsonl` at the time of the last status
/// change. **Not serialized** — recomputed on every open so it cannot
/// drift from the truth on disk.
#[serde(skip)]
pub source_changed_since_review: bool,
```

### 1.1 `ReviewStatus`

```rust
// crates/core/src/review.rs — new module

use serde::{Deserialize, Serialize};

/// Reviewer-process state of a translation unit.
///
/// Orthogonal to [`UnitState`] — a unit can be `(UnitState::Proposed,
/// ReviewStatus::Approved)` (a confirmed translation that the catalog
/// still marks `type="unfinished"` because the team has not yet decided
/// to graduate it to `Finished`).
///
/// Variants are listed in the rough order a unit progresses through a
/// translator's pipeline, but transitions are *not* a strict linear
/// state machine: a reviewer can move a unit from `Reviewed` back to
/// `NeedsReview` by clicking "request another look", or jump from
/// `MachineTranslated` directly to `Approved` on accept-as-is.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Serialize, Deserialize)]
#[serde(rename_all = "kebab-case")]
pub enum ReviewStatus {
    /// No machine or human work has touched this unit yet.
    /// Set when: a freshly-extracted unit is first persisted to the
    /// review store, e.g. on first manual save of a new catalog. Not
    /// the default for an un-touched unit — the *absence* of a record
    /// in `review.jsonl` is the default; `New` is set when something
    /// has affirmatively claimed the unit (a translator opened it,
    /// gave it a flag, etc.) but no MT or review has run.
    New,
    /// A machine translation backend produced a target. Set when:
    /// `Project::set_review_status` is called with `MachineTranslated`
    /// at the end of a successful `translate_unit` / `translate_batch`
    /// when the gate is clean and no `Flag` triggered a review
    /// request. The bulk-translate flow in M4.8 lands units here.
    MachineTranslated,
    /// A machine translation produced flags, or a translator/reviewer
    /// explicitly requested a second look. Set when: the gate or
    /// backend produced any [`crate::Flag`] of severity Hard or Warn
    /// on the unit's MT proposal (M4.6), or the UI invokes
    /// `Project::set_review_status(..., NeedsReview)` explicitly.
    NeedsReview,
    /// A human reviewer looked at the unit and accepted it without
    /// declaring it final. Set when: the UI's "Accept" action runs on
    /// a flagged unit.
    Reviewed,
    /// A human declared this translation final for the current source.
    /// Set when: the UI's "Save All" action persists a unit whose
    /// gate is clean and whose review state is `Reviewed` or
    /// `MachineTranslated`. Cleared (back to `NeedsReview`) when the
    /// source changes — see §6.
    Approved,
    /// `Approved` plus "do not re-translate by machine". Set when:
    /// `Project::set_review_status(..., Locked)` is called explicitly
    /// from the UI. Bulk-translate (M4.8) skips locked units;
    /// `translate_unit` on a locked unit returns the existing target
    /// unchanged. Treated as `Approved` everywhere else.
    Rejected,
    /// A human looked at the unit and concluded the MT proposal is
    /// wrong but did not supply a replacement. Set when: the UI's
    /// "Reject" action runs.
    Locked,
    /// Two or more reviewers gave the same unit contradictory edits
    /// since the last save. Reserved for M4.x multi-reviewer
    /// extensions; for v1 the variant exists in the enum but is never
    /// set automatically — leaving it in the API surface now prevents
    /// a breaking change later.
    Conflict,
}
```

(Note: the variant order in the type declaration matches the
[`feedback-2026-05-24-chatgpt.md`](feedback-2026-05-24-chatgpt.md) §1
list — `New | MachineTranslated | NeedsReview | Reviewed | Approved |
Locked | Rejected | Conflict`. I have re-ordered `Locked` and
`Rejected` in the doc-comment narrative above to make the lifecycle
flow read top-to-bottom; **the enum declaration follows the
user-input order verbatim**, so external users of the enum see the
same set the spec promised.)

### 1.2 `Unit` constructor changes

`Unit::untranslated_singular` continues to set `source_hash: None`,
`review_status: None`, `source_changed_since_review: false`. No new
constructor is added — adapters fill the new fields by struct-update on
the existing field-by-field construction in
[`crates/adapter-qt/src/parse.rs:322-331`](../crates/adapter-qt/src/parse.rs).

### 1.3 Module placement

- `ReviewStatus` lives in a **new module** `crates/core/src/review.rs`
  and is `pub use`'d from `crates/core/src/lib.rs`. Rationale: it is
  conceptually distinct from `UnitState` (catalog state vs reviewer
  state) and small enough to live in its own file. Co-locating it with
  `UnitState` in `unit.rs` would invite implementers to confuse the
  two.
- `source_hash` and `source_changed_since_review` are fields on the
  existing `Unit` struct in `unit.rs`. They are not their own type.

### 1.4 Serde shape and defaults

| Field | Type | `serde` attrs |
|---|---|---|
| `source_hash` | `Option<String>` | `#[serde(default, skip_serializing_if = "Option::is_none")]` |
| `review_status` | `Option<ReviewStatus>` | `#[serde(default, skip_serializing_if = "Option::is_none")]` |
| `source_changed_since_review` | `bool` | `#[serde(skip)]` |

The `skip_serializing_if` on the two `Option` fields means existing
`Intermediate` JSONL fixtures stay byte-stable: a `Unit` serialized
before this change deserializes cleanly (defaults to `None`), and a
`Unit` with both fields `None` re-serializes without those keys.

The `skip` on `source_changed_since_review` is load-bearing: this is a
**derived** field, computed at open time. Persisting it would invite
the value on disk to disagree with the truth (the comparison against
`source_hash`), and that disagreement would surface as a bug we cannot
test for.

## 2. `source_hash` algorithm

### 2.1 What gets hashed

| Component | In hash? | Rationale |
|---|---|---|
| `source` (ICU-normalized) | **Yes** | The translation target. Trivially yes. |
| `disambiguation` (Qt `<comment>`) | **Yes** | The Qt mechanism for "same source, different meaning"; changing it changes the unit's *meaning*. |
| `extracomment` (Qt `<extracomment>`) | **Yes** | The developer's natural channel for "I want translators to re-read this." A change here is a deliberate request for re-review. |
| `context` (Qt `<context name="…">`) | **No** | The context name is already part of `UnitId` (see [`parse.rs:283-287`](../crates/adapter-qt/src/parse.rs)). Two units with the same source in different contexts are *different units*, not "source changed" of the same unit. If a developer renames `FileMenu` → `FileActions` without changing strings, the `UnitId` changes — that is a *new unit added, old unit vanished* event, handled by the existing extract+apply flow, not by `source_hash` invalidation. |
| `location` (file path + line) | **No** | Routine refactors (file moves, line shifts) trigger churn the translator has no business re-reviewing. The user-input doc proposed including it; my call is to exclude it on the grounds that it over-triggers. We can promote it to a soft signal (a UI badge "moved since approval") in a later milestone without touching the hash. |
| `numerus` flag (singular vs plural) | **Yes** | A unit changing from singular to plural is a structural source change the translator *must* re-review (the gate would already reject the existing target against the new plural arity, but the hash invalidation surfaces the situation pre-translate). |

### 2.2 Hash function and encoding

```
component_bytes = source       ‖ 0x1F
                ‖ disambiguation ‖ 0x1F
                ‖ extracomment   ‖ 0x1F
                ‖ "P" if plural else "S"

digest = SHA-256(component_bytes)
source_hash = "sha256:" + hex(digest)[..12]
```

Where:

- `‖` is concatenation.
- `0x1F` is the ASCII unit-separator control character; it is rare
  enough in natural language that using it as a field separator is
  unambiguous. (Compare `CorrectionId`'s use of `\0` in
  [`memory.rs:84-94`](../crates/project/src/memory.rs) — same idea,
  different separator because `0x1F` is safer to embed in human-readable
  text on the off chance we ever log the pre-image.)
- An empty optional component contributes its empty string plus the
  separator; this distinguishes `(source="X", comment="")` from
  `(source="X", comment=None)` because the latter is impossible — we
  *always* include the separator, and an absent comment is the empty
  string.
- The plural/singular suffix is a single ASCII byte so the pre-image is
  unambiguous regardless of the source text.

### 2.3 Why the `"sha256:"` prefix

Two reasons:

1. **Algorithm agility.** If a future need (cross-project translation
   memory, larger corpora) forces a longer or different hash, the
   prefix lets us add `"blake3:"` or `"sha256-24:"` without ambiguity
   on read. Old stored hashes keep working because the comparison is
   string-equality; new units start emitting the new prefix.
2. **Greppability in `review.jsonl`.** Diagnosing a stuck "source
   changed" indicator is much easier when you can `rg sha256:` and see
   the field, vs a bare 12-char hex blob that could be anything.

Cost: 7 bytes per unit at rest. Negligible.

### 2.4 Truncation to 48 bits

Same logic as `CorrectionId`'s 12-char truncation
([`memory.rs:96-99`](../crates/project/src/memory.rs)). The hash is
scoped to a single project's corpus, optimistically 10k units. Birthday
bound: ~2^24 records before a 1% collision risk — three orders of
magnitude above the realistic corpus size.

A collision would manifest as "edited the source but the indicator did
not fire." This is a soft-fail (the translator can still re-translate
manually) and the surrounding gate checks would catch a stale target
that no longer matches the new placeholder set. Not worth defending
against with a longer hash.

### 2.5 Why this is not user-configurable

The set of components included in the hash is part of the contract
between the adapter and the review store. A project that customized it
would invalidate every prior review record on the next open, with no
recovery path. The "I want location in the hash too" knob is the kind
of feature that sounds harmless until two checkouts of the same project
disagree about which units are stale.

If a real user need surfaces (e.g., projects where developer comments
churn for non-translation reasons), the fix is a *new* hash variant
with its own prefix, run alongside the existing one — not a knob on the
existing variant.

## 3. `adapter-qt::extract` changes

### 3.1 What the parser captures

The Qt parser in [`crates/adapter-qt/src/parse.rs`](../crates/adapter-qt/src/parse.rs)
already captures `source` and the disambiguation `<comment>` (the
`comment` local at [`parse.rs:182`](../crates/adapter-qt/src/parse.rs)).
It does **not** today capture `<extracomment>` — that element is
swallowed by the catch-all `skip_to_close` arm at
[`parse.rs:246-251`](../crates/adapter-qt/src/parse.rs).

M4.1.5 adds a new `extracomment: Option<String>` local in
`parse_message`, populated by a new match arm:

```rust
QName(b"extracomment") => {
    let txt = read_text_until_close(reader, b"extracomment")?;
    extracomment = Some(txt);
}
```

The `extracomment` text is **not** added to `Unit` as a field (the
core `Unit` shape stays as-is plus the three M4.1.5 additions). It is
used only to compute `source_hash` and then dropped. The catalog's
byte-stability is unaffected because we are reading, not writing.

If a `<message>` contains multiple `<extracomment>` elements (Qt
permits this), we concatenate them with a single `\n` in source-order
before hashing. Qt's behavior is to display them concatenated; we
mirror it.

### 3.2 Where `source_hash` is computed

A new free function lives at `crates/core/src/unit.rs` (so PO and
ICU-JSON adapters use the same algorithm without each importing the
adapter-qt crate):

```rust
/// Compute the M4.1.5 source hash for a unit.
///
/// `disambiguation` and `extracomment` are the empty string when the
/// catalog format does not record them (PO has no Qt-style comment
/// distinction; ICU-JSON typically has neither). The plural flag is
/// derived from the unit's `plural_arity.is_some()`.
///
/// See `docs/m4.1.5-source-hash-review-status-design.md` §2 for the
/// algorithm and the rationale for what is and is not hashed.
pub fn compute_source_hash(
    source: &str,
    disambiguation: &str,
    extracomment: &str,
    plural: bool,
) -> String { /* … */ }
```

`adapter-qt::parse_message` calls this with the captured strings before
constructing the `Unit`, then sets `unit.source_hash = Some(hash)`.

### 3.3 Vanished and obsolete units

Units with `state ∈ {Vanished, Obsolete}` get `source_hash = None`.
Rationale: the harness never translates these (the round-trip preserves
them verbatim), so a stale-source indicator is meaningless. Storing a
hash for them would waste write-back churn when a user converts a
vanished entry back to active (re-extract → new hash → spurious
"source changed" alert). `None` collapses this case cleanly.

The check is one line in `parse_message`: skip the
`compute_source_hash` call when `state_from_attr` is `Vanished` or
`Obsolete`.

### 3.4 Round-trip impact

None. The parser still reads `<extracomment>` via the same
byte-preserving path the catch-all uses (we replace `skip_to_close`
with `read_text_until_close` for that one tag name; the underlying
reader still walks the same bytes). `apply` continues to splice only
the translation body and the `type` attribute; `<extracomment>` is
preserved by the byte-stability mechanism, unchanged.

A new fixture under `crates/adapter-qt/tests/fixtures/` exercises a
catalog with `<extracomment>` text to confirm the round-trip stays
byte-stable and the computed hash includes that text.

## 4. `ReviewStatus` lifecycle — when each variant is set

The harness sets review status from these surfaces. Anything not listed
leaves the field unchanged.

| Action | Pre-condition | Post review_status |
|---|---|---|
| Catalog opened, unit has no record in `review.jsonl` | — | `None` (UI displays as "New" but persisted state is absent) |
| User edits a unit's target text manually in the UI, then "Save" | The unit had no record OR record was `New` | `New` (a record is now present; nothing has reviewed it) |
| `translate_unit` succeeds, gate clean, zero flags | — | `MachineTranslated` |
| `translate_unit` succeeds, gate produced flags OR backend produced flags | — | `NeedsReview` |
| `translate_batch` succeeds for a unit, gate clean, zero flags | — | `MachineTranslated` |
| `translate_batch` succeeds for a unit, gate dirty OR flags present | — | `NeedsReview` |
| User clicks "Accept" on a flagged unit in the inspector | Unit is `NeedsReview` or `MachineTranslated` | `Reviewed` |
| User clicks "Save All" on a catalog | Unit is `Reviewed` and gate is clean | `Approved` |
| User clicks "Save All" on a catalog | Unit is `MachineTranslated` and gate is clean | `Approved` (one-click accept-as-final) |
| User clicks "Reject" on a unit's MT proposal | — | `Rejected` |
| User clicks "Lock" on an approved unit | Unit is `Approved` or `Reviewed` | `Locked` |
| User clicks "Unlock" on a locked unit | Unit is `Locked` | `Approved` |
| Source-hash mismatch detected on open | Unit was `Reviewed`, `Approved`, or `Locked` | Status unchanged; `source_changed_since_review = true` (see §6) |
| User explicitly "Mark for review" on any unit | Any | `NeedsReview` |
| User explicitly re-approves a stale-source unit | `source_changed_since_review == true` | Status unchanged; `source_changed_since_review = false` (see §6.3) |

`Conflict` is reserved for M4.x multi-reviewer extensions; no v1
surface sets it.

The transitions above are owned by the **caller** of
`Project::set_review_status`, not by `Project` itself. The project
crate's job is to persist whatever status the caller hands it (with
the source-hash bookkeeping); the decision of *which* status to write
belongs to the layer that knows what the user did — the Tauri
command (M4.2) for UI-driven transitions, the bulk-translate runner
(M4.8) for MT-driven transitions. **The project crate does not embed
a state machine** because the rules above straddle multiple crates
(gate decides "clean", backend reports flags, UI interprets clicks)
and embedding the machine would force every caller through a single
contract that the project crate cannot validate without all that
context.

## 5. Persistence — Option B (single project-wide JSONL)

### 5.1 The pick

`<state_dir>/review.jsonl`, single project-wide append-only JSONL,
folded last-write-wins per `(catalog, unit_id)` on read.

The factors that drove the call:

- **Audit trail.** A translator-facing tool benefits from "when did
  this go from `NeedsReview` to `Approved` and who did it." The
  append-only log preserves this for free. Option A (per-catalog TOML
  with current-state-only) drops it entirely.
- **Schema evolution.** One file with one schema version is much
  easier to migrate than N files. The M4.1d corrections store already
  uses the same pattern ([`memory.rs:234-334`](../crates/project/src/memory.rs)),
  and the project crate already has the read/append plumbing — Option
  B reuses it.
- **Read cost on project open.** A 10k-review JSONL is a few hundred
  KiB, scans in milliseconds (same logic as the corrections store —
  see [`m4.1-project-crate-design.md` §6.1](m4.1-project-crate-design.md#61-correctionsjsonl-shape-and-keying)).
  The fold-to-map step happens once on open and caches in memory.
- **Crash safety.** Single-line atomic appends (lines stay under
  `PIPE_BUF`) are the same crash-safety story as
  `corrections.jsonl` and `metrics.jsonl`. No write-ordering edge
  cases.
- **Edit-by-hand ergonomics.** JSONL is greppable; a reviewer who
  wants to find "every unit I approved on 2026-05-24" runs `rg
  '"status":"approved".*2026-05-24' review.jsonl`. Option A's
  per-catalog TOML is friendlier for manual editing of one unit but
  worse for cross-catalog queries — and cross-catalog is the M4.7
  review queue's whole point.

### 5.2 Why not Option C (fold into `corrections.jsonl`)

`corrections.jsonl` records *content edits* (human typed a different
translation). Review-status changes are *process edits* (human clicked
Approve without changing text). Conflating them in one schema would:

1. Force every reader to discriminate on `kind` even when it only
   wants content edits — adds branching cost to the M4.9 Quality tab
   and the M4.10 tuning bundle export, neither of which cares about
   process edits.
2. Pollute the M4.10 tuning bundle, which exports curated
   corrections-as-training-examples; a "process edit" example is
   noise in that pipeline.
3. Break the existing `Correction` schema's content-hash id
   ([`memory.rs:55-72`](../crates/project/src/memory.rs)) — that id
   includes `mt_proposal` and `human_target`, which are not present
   on a pure status change.

Two files, two schemas. Same plumbing pattern, distinct concerns.

### 5.3 On-disk shape

One JSON object per line. Newlines inside string values are escaped by
`serde_json` as `\n`, never literal — same invariant as
[`memory.rs:264-267`](../crates/project/src/memory.rs).

```json
{"schema":1,"ts":"2026-05-24T12:34:56.123456Z","catalog":"translations/app_de.ts","unit_id":"MainWindow::Hello","status":"approved","source_hash":"sha256:a1b2c3d4e5f6","reviewer_note":"Confirmed against the v3.2 mockup."}
```

Field shape:

```rust
/// One review-status change event. Append-only; last write per
/// `(catalog, unit_id)` wins on fold.
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct ReviewEvent {
    /// Schema version for this line shape. Currently `1`.
    pub schema: u32,
    /// RFC 3339 microsecond UTC ts of the status change.
    pub ts: String,
    /// Manifest-relative path to the catalog (so events survive a
    /// project move or root rename — same convention as `Correction`).
    pub catalog: PathBuf,
    /// Unit within the catalog.
    pub unit_id: UnitId,
    /// The new status. Use `Option<ReviewStatus>` (serialized as `null`)
    /// to record a deliberate "clear this unit's record" event; the
    /// fold treats `null` as "remove this unit from the in-memory map."
    pub status: Option<ReviewStatus>,
    /// The unit's `source_hash` at the moment the reviewer approved it.
    /// This is the value the load-time check (§6) compares the current
    /// extract's hash against. Empty string when the unit's adapter
    /// produces no hash (PO/ICU-JSON in early M4).
    #[serde(default, skip_serializing_if = "String::is_empty")]
    pub source_hash: String,
    /// Free-form reviewer note attached to this status change. Empty
    /// when not provided. Surfaces in the M4.7 review queue and the
    /// M4.9 Quality tab.
    #[serde(default, skip_serializing_if = "String::is_empty")]
    pub reviewer_note: String,
}
```

Schema rationale points:

- `status: Option<ReviewStatus>` lets us record a "clear" event without
  inventing a sentinel variant. A future "the user demoted this from
  `Approved` back to undecided" UI action becomes one append with
  `status: null` — the fold removes the entry. (We do not expect this
  to fire often, but designing it in costs nothing.)
- `schema: 1` mirrors `Correction.schema`; same migration story.
- `catalog` is manifest-relative for the same reason as `Correction`:
  the project survives `cp -r`.

### 5.4 Load — `ReviewStore::read_folded`

```rust
/// Fold the append-only log into the current `(catalog, unit_id) →
/// (ReviewStatus, source_hash_at_review, ts, reviewer_note)` view.
///
/// Reads every line; the last well-formed event for a given key wins.
/// `Option::None` status events remove the key from the result.
///
/// Malformed lines are reported in the warnings vec; the store is
/// line-recoverable.
pub fn read_folded(
    &self,
) -> Result<(BTreeMap<(PathBuf, UnitId), ReviewRecord>, Vec<ProjectError>), ProjectError>;

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ReviewRecord {
    pub status: ReviewStatus,
    pub source_hash_at_review: String,
    pub ts: String,
    pub reviewer_note: Option<String>,
}
```

The map key is `(catalog_manifest_relative, unit_id)`. The fold is
O(N) over the file; for N ~ 10k records the cost is ~1ms on commodity
hardware. The map is cached on `Project` and invalidated when
`set_review_status` appends — see §7.4 for the cache invalidation.

### 5.5 Append — `ReviewStore::append`

Mirrors `CorrectionStore::append`:

```rust
pub fn append(&self, event: &ReviewEvent) -> Result<(), ProjectError>;
```

Single line, atomic append via `ProjectFs::append`. Lines stay under
~4 KiB (the largest field is `reviewer_note`, which the UI caps at
~500 chars).

### 5.6 Compaction

**Not in v1.** The roadmap accepts unbounded growth at translator
throughput — a heavily-used project might accumulate 50k events over
several years, still in the hundreds-of-KiB range. If a real
deployment hits a real cost, the answer is a `harness review compact`
CLI command that reads the folded view and writes a fresh
`review.jsonl` with one current-state event per key, dropping the
history. That is a follow-up milestone, not a blocker for M4.1.5.

The compaction story mirrors `corrections.jsonl` exactly
([`m4.1-project-crate-design.md` §6.1](m4.1-project-crate-design.md)).

### 5.7 Interaction with `cp -r` portability

Same as `corrections.jsonl`: the file lives under `<state_dir>/`,
which defaults to `<root>/.i18n-harness/`. A `cp -r` of the project
root carries the review state along, and the manifest-relative
`catalog` field means the events resolve correctly against the copied
catalogs. If the user pointed `[paths] state_dir` at a per-machine
absolute path, the state stays on the original machine — same gotcha
documented in [`m4.1-project-crate-design.md` §7.2](m4.1-project-crate-design.md#72-portability-of-the-manifest).

## 6. Invalidation rule — Option Y

### 6.1 The pick

When the current extract's `source_hash` differs from
`ReviewRecord.source_hash_at_review`:

- **Keep the prior status unchanged.**
- **Set `Unit.source_changed_since_review = true`** (the derived field
  from §1.4) so the UI can decorate the unit with a "source changed
  since approval" indicator.

The translator sees: status badge "Approved" plus a small "source
changed" marker; the inspector shows a diff of the old hash's
pre-image and the new one (M4.7 work).

This preserves the translator's agency. Silent demotion (Option X)
loses the trail of "I approved this last Tuesday"; promotion to a new
`StaleApproval` variant (Option Z) bloats the enum for what is really
a per-unit boolean orthogonal to status.

### 6.2 Where the comparison happens

In **`Project::open_catalog`** (the call the M4.2 Tauri command layer
makes per catalog, not the `Project::open` step that loads the
manifest). The shape:

```rust
// pseudo-code in the consumer (M4.2 Tauri command), wiring the
// adapter, the project, and the unit:

let extracted_units = adapter_qt::extract(&catalog_abs_path)?.units;
let review_map = project.review_map(); // cached in Project; see §7
for unit in &mut extracted_units {
    let key = (catalog_manifest_path.clone(), unit.id.clone());
    if let Some(record) = review_map.get(&key) {
        unit.review_status = Some(record.status);
        if let (Some(current), prior) = (&unit.source_hash, &record.source_hash_at_review) {
            unit.source_changed_since_review = current != prior;
        }
    }
}
```

The project crate provides the `review_map` and a helper
`Project::apply_review_state(catalog_manifest_path, &mut [Unit])` so
consumers do not write this loop themselves. See §7.

### 6.3 When `source_changed_since_review` becomes `false` again

Exactly one event: the user explicitly re-approves the unit (UI
action: "Re-approve at current source"). The Tauri command layer
turns this into:

```
Project::set_review_status(
    catalog_manifest_path,
    unit_id,
    Some(unit.review_status),  // unchanged
    unit.source_hash.clone(),  // CURRENT hash, replacing the stale one
    reviewer_note: Some("Re-approved at new source")
);
```

The append updates `source_hash_at_review` to the current value;
the next `apply_review_state` call computes `current == prior` and
clears the flag.

**A target edit alone does not clear it.** If the translator edits the
target text in response to a source change, the UI prompts "this
clears the source-changed marker — confirm?" before persisting. The
explicit click is the load-bearing UX moment that distinguishes
"I edited because I wanted to" from "I missed the source change
warning."

### 6.4 Status of new units (no prior record)

`source_changed_since_review = false`. There is nothing to be stale
against. `review_status` stays `None`.

### 6.5 Status when the adapter produces no `source_hash`

If `Unit.source_hash == None` (PO/ICU-JSON adapters in early M4, or
a vanished/obsolete unit), `apply_review_state` leaves
`source_changed_since_review = false` regardless of the stored
`source_hash_at_review`. We do not synthesize a comparison when we
cannot honestly make one. The review status itself still applies — the
translator's approval stands.

## 7. `Project` API additions

The following lands on `Project` in `crates/project/src/project.rs`,
alongside the existing `record_correction` / `list_corrections` /
`promote_to_curated` block. Each method follows the existing pattern:
error type is `ProjectError`, no `async`, methods take `&self` unless
mutation of cached state is required.

### 7.1 The review store

```rust
impl Project {
    /// Borrow the project's review store. Cheap; I/O happens on
    /// [`ReviewStore::append`] and [`ReviewStore::read_folded`].
    pub fn reviews(&self) -> &ReviewStore;
}
```

Created on `Project::open`, same pattern as `CorrectionStore` (see
[`project.rs:631-633`](../crates/project/src/project.rs)).

### 7.2 Setting a status

```rust
impl Project {
    /// Record a review-status change.
    ///
    /// Generates `ts` from `SystemTime::now`, builds a [`ReviewEvent`]
    /// with `schema = 1`, serialises it as one-line JSON, and appends
    /// it to `<state_dir>/review.jsonl`. Invalidates the cached
    /// fold (§7.4) so the next `apply_review_state` sees the new value.
    ///
    /// `status = None` is a deliberate "clear this unit's record" event
    /// — see [`ReviewEvent::status`] for the fold semantics.
    ///
    /// # Errors
    ///
    /// - [`ProjectError::Io`] if the append fails.
    /// - [`ProjectError::UnknownCatalog`] if `catalog` is not in
    ///   `self.catalogs()`.
    pub fn set_review_status(
        &self,
        catalog: &Path,
        unit_id: &UnitId,
        status: Option<ReviewStatus>,
        source_hash_at_review: String,
        reviewer_note: Option<String>,
    ) -> Result<(), ProjectError>;
}
```

The signature takes `source_hash_at_review` explicitly (rather than
re-deriving it from a `Unit`) because the project crate does not own
the `Unit` value — the caller does, and threading it through the call
keeps the project crate ignorant of unit shape changes. This also
makes the "re-approve at current source" flow (§6.3) trivial: the
caller passes the current `unit.source_hash.clone().unwrap_or_default()`.

`reviewer_note: Option<String>` is converted to empty-string for the
on-wire shape (matches `CorrectionProvenance` precedent).

### 7.3 Reading status

```rust
impl Project {
    /// Look up the current review status for one unit. Convenience over
    /// `reviews().read_folded()` for one-off lookups.
    ///
    /// Returns `None` if the unit has no record.
    pub fn review_status_of(
        &self,
        catalog: &Path,
        unit_id: &UnitId,
    ) -> Option<ReviewRecord>;

    /// Return the folded view: every `(catalog, unit_id)` with a
    /// current record. Cached; cleared by `set_review_status`.
    pub fn review_map(&self) -> &BTreeMap<(PathBuf, UnitId), ReviewRecord>;

    /// Populate `unit.review_status` and `unit.source_changed_since_review`
    /// for every unit in `units` based on the current fold and each
    /// unit's `source_hash`. Idempotent.
    ///
    /// This is the load-bearing helper for the M4.2 Tauri layer —
    /// every catalog-open call site routes the extracted units through
    /// it before handing them to the UI.
    pub fn apply_review_state(
        &self,
        catalog: &Path,
        units: &mut [Unit],
    );
}
```

`review_status_of` and `review_map` return owned/borrowed views from
the same cache; the implementation uses `RefCell` or `OnceCell`
internally to keep the public API non-mutable. (Same pattern as the
existing `CuratedSet` cache in
[`project.rs`](../crates/project/src/project.rs).)

### 7.4 Cache invalidation

`Project` holds an `OnceCell<BTreeMap<(PathBuf, UnitId), ReviewRecord>>`
populated on first `review_map()` call. `set_review_status` invalidates
this cell by clearing it after a successful append, so the next read
re-folds the file. This costs one full read per status change; for
the size we expect (~10k records, ~milliseconds), this is acceptable
and avoids the bug class of "cache lied because the in-process write
went into the cache but a sibling process appended to the file."

If profiling shows this is too expensive in a bulk-translate flow that
sets thousands of statuses in a row (M4.8), the M4.8 implementer can
add a `Project::with_batch_review_updates(closure)` that defers the
invalidation to the closure boundary. **Not in M4.1.5 scope.**

### 7.5 New error variants

```rust
// crates/project/src/error.rs additions

#[derive(Debug, thiserror::Error)]
pub enum ProjectError {
    // … existing variants …

    /// A review-status operation referenced a catalog that is not in
    /// the manifest. Caller: ensure the catalog is registered via
    /// `add_catalog` before recording reviews against it.
    #[error("review op references unknown catalog: {}", path.display())]
    UnknownCatalog {
        /// Manifest-relative or absolute path that did not match a
        /// known `[[catalogs]]` entry.
        path: PathBuf,
    },

    /// A JSONL line in `review.jsonl` cannot be parsed. The store is
    /// line-recoverable — the fold skips the bad line and surfaces this
    /// error rather than aborting.
    #[error("malformed review event line {line_no} in {}: {source}", path.display())]
    ReviewEventParse {
        /// File that contains the bad line.
        path: PathBuf,
        /// 1-based line number of the bad record.
        line_no: usize,
        /// Underlying JSON error.
        source: serde_json::Error,
    },
}
```

Both variants follow the existing `ProjectError` pattern — single enum,
`thiserror`, `#[error(...)]` with path context. No
`#[error(transparent)]` because the underlying types do not carry
enough context on their own.

### 7.6 Exports

`crates/project/src/lib.rs` gains:

```rust
pub use crate::review::{ReviewEvent, ReviewRecord, ReviewStore};
```

(`ReviewStatus` itself is re-exported from `i18n_harness_core`, not
the project crate; the project crate accepts and stores the enum but
does not own it.)

## 9. Test plan

### 9.1 `crates/core`

- **Unit test:** `compute_source_hash("Open file", "menu", "", false)`
  is stable across calls (returns the same string on repeated
  invocation).
- **Unit test:** changing `source` changes the hash; changing
  `disambiguation` changes the hash; changing `extracomment` changes
  the hash; flipping `plural` changes the hash.
- **Unit test:** the hash format matches `^sha256:[0-9a-f]{12}$`.
- **Unit test:** the hash for an empty-source unit
  (`source=""`, `disambiguation=""`, `extracomment=""`, `plural=false`)
  is deterministic and documented (we don't care what value, only that
  it's stable — pin it in a test so we notice if someone changes the
  algorithm).
- **Property test (proptest):** for random `(source, disambiguation,
  extracomment, plural)` tuples, two different tuples produce
  different hashes with overwhelming probability (run 1000 cases;
  collisions should not appear).
- **Serde round-trip test:** a `Unit` with all-`None` review fields
  serializes/deserializes to an identical `Unit`; a `Unit` with
  `source_hash = Some(...)` and `review_status = Some(Approved)`
  round-trips identically; `source_changed_since_review` is *not*
  in the serialized form (the field is set to `false` on read
  regardless of any prior value).
- **Backward-compat test:** an existing `Intermediate` JSONL fixture
  produced before this change deserializes cleanly with the new
  fields defaulting to their `None`/`false`.

### 9.2 `crates/adapter-qt`

- **Round-trip:** every existing fixture stays byte-identical (the
  M0 contract).
- **New fixture:** a `.ts` file with one unit carrying a
  `<extracomment>` (use the existing `showcase.ts` as the base — it
  already has one at line 19). On extract, the unit's `source_hash`
  is `Some(...)`. Modify the fixture in a sibling file to change the
  `<extracomment>` text only; the two units' hashes differ.
- **Vanished/obsolete:** the `showcase.ts` fixture's vanished and
  obsolete units have `source_hash = None`. (One assertion per state.)
- **Plural hash:** a numerus message and a singular message with the
  same source text have different hashes (the plural-flag suffix
  ensures this).
- **Multiple extracomments:** a synthetic fixture with two
  `<extracomment>` blocks produces a hash equal to the one with the
  same blocks joined by `\n` (codifies §3.1).

### 9.3 `crates/project`

- **`ReviewStore::append` + `read_folded`:** appending three events
  for the same `(catalog, unit_id)` returns one record reflecting the
  last event in the folded map.
- **`ReviewStore::read_folded` line recovery:** a JSONL file with one
  malformed line returns the well-formed records and one
  `ReviewEventParse` in the warnings vec.
- **`Project::set_review_status` + `review_status_of`:** set a status,
  read it back, value matches. Set a second status for the same unit;
  read it back; the second value wins.
- **`Project::set_review_status` with `status: None`:** the unit
  disappears from `review_map`.
- **`Project::apply_review_state`:** given a `[Unit]` with `source_hash
  = Some("sha256:aaaa...")` and a stored record with
  `source_hash_at_review = "sha256:aaaa..."`, the unit's
  `source_changed_since_review` is `false`. With a different stored
  hash, it is `true`. With `Unit.source_hash = None`, it is `false`
  regardless of the stored hash.
- **Cache invalidation:** call `review_map()`, call
  `set_review_status` for some unit, call `review_map()` again — the
  new status is visible. (Tests the §7.4 cache-clear-on-write.)
- **Path resolution:** `ProjectPaths::review()` resolves to
  `<state_dir>/review.jsonl` for both the default and the
  `[paths] state_dir` override case.
- **`UnknownCatalog`:** `set_review_status` against a catalog path
  that is not in the manifest returns
  `ProjectError::UnknownCatalog`.
- **`InMemoryFs` parity:** every public method runs on both `RealFs`
  (via `tempfile`) and `InMemoryFs` with matching output. (Same
  contract as the M4.1 test suite.)

### 9.4 Cross-crate integration

A single test that exercises the full slice:

1. Construct a `Project` over a temp dir with one Qt fixture.
2. Extract the catalog through `adapter_qt::extract`; verify every unit
   has `source_hash = Some(...)`.
3. Call `Project::apply_review_state` over the units; verify
   `review_status = None`, `source_changed_since_review = false`.
4. Call `Project::set_review_status` for one unit with `status =

5. Re-extract, re-apply; verify that unit's `review_status =

6. Mutate the fixture's `<source>` text for that unit; re-extract,

7. Call `Project::set_review_status` again with the *new* `source_hash`

New items added to public surfaces. Marking each `pub` decision against

### 11.1 `crates/core` — keep `pub`

- `Project::reviews`, `set_review_status`, `review_status_of`,

  analogue to `NewCorrection`). `set_review_status` is the public
  entry point; it builds the event internally so callers cannot forge

## 12. Trade-offs weighed and which I picked

### 12.1 Hash inputs: `source + disambiguation + extracomment + plural-flag` vs the user-input proposal

The user-input doc (`feedback-2026-05-24-chatgpt.md` §2) proposed
`context + source + disambiguation/comment + location`. I rejected
`context` and `location`, added the `plural` flag.

- **Context excluded** because it is already part of `UnitId` — a
  context rename produces a new unit id, which the existing
  extract/apply machinery already treats as "old unit vanished, new
  unit added." Putting context in the hash would either double-count
  (the unit *id* would already have changed) or create a confusing
  "the source hash changed but the unit id stayed the same" case
  that cannot actually happen.
- **Location excluded** because file moves and line shifts churn
  during routine refactors; making them invalidate reviews would
  over-trigger to the point translators ignore the indicator. If
  there is later demand for "show me what moved since my last
  approval," the answer is a separate `location_changed_since_review`
  signal, not folding location into the hash.
- **Plural flag included** because a singular→plural source change is
  exactly the kind of structural shift a translator must re-evaluate.
  The gate would already reject a target against the wrong arity, but
  the hash invalidation surfaces the situation in the queue.

**Rejected alternative:** *no extracomment, only source + disambiguation.*
This was my first instinct in the question. Reason for moving off it:
the developer comment IS the natural channel for "I changed this in a
way that matters to the translator." Excluding it would force
developers to invent a workaround (modify whitespace in the source
string?) to get the harness to flag for re-review.

### 12.2 Persistence: Option B (single JSONL) over A (per-catalog TOML) and C (folded into `corrections.jsonl`)

- **Option A (per-catalog TOML)** loses the audit trail and complicates
  cross-catalog queries (the M4.7 review queue's whole job). Wins on
  edit-by-hand ergonomics for one unit; loses on every other axis.
- **Option C (fold into `corrections.jsonl`)** conflates content edits
  with process edits in one schema. Forces every reader of
  `corrections.jsonl` to discriminate on `kind`. Pollutes the M4.10
  tuning bundle pipeline. The shared schema is more cost than the
  saved file is worth.
- **Option B (single JSONL)** reuses the proven pattern from
  `corrections.jsonl` + `metrics.jsonl`, preserves audit trail,
  supports cross-catalog queries cheaply, and the I/O cost is in line
  with the other JSONL stores. **Picked.**

The compaction story (§5.6) accepts unbounded growth as the v1 answer
on the same grounds as `corrections.jsonl` — translator throughput is
low enough that "no compaction" beats "premature compaction."

### 12.3 Invalidation: Option Y (preserve status + flag) over X (silent demote) and Z (new variant)

- **Option X (silent demote)** loses the translator's work history.
  The user clicked Approve; the harness should not unclick it without
  asking. This is the kind of "small UX paper cut that erodes trust"
  the maintainer's lab framing explicitly cares about.
- **Option Z (new `StaleApproval` variant)** bloats the enum from 8 to
  9 variants for what is really `(status, source_changed: bool)`.
  Every `match` against `ReviewStatus` would have to handle the new
  variant or risk the compiler missing it. Costs a lot of churn for a
  state that is conceptually a flag, not a status.
- **Option Y (separate `source_changed_since_review` field)** keeps
  the two concerns orthogonal. The translator sees both badges and
  can act independently — re-approve, edit-and-re-approve, demote to
  `NeedsReview`. **Picked.**

The Option Y design hinges on the field being **derived, not
persisted** (§1.4). Storing it would invite drift; deriving it from
the comparison at open time keeps it as honest as the comparison
itself.

### 12.4 Where the state-transition rules live

I considered embedding the transitions from §4 in
`Project::set_review_status` (as a state-machine guard that rejects
invalid transitions). I rejected this because the *legal* transition
depends on facts the project crate cannot see — the gate's verdict
on the unit's target, whether a flag is present, whether a translator
clicked "Accept" or "Reject" or "Save All." Asking the project crate
to validate transitions would force every caller to pass all that
context through, which is exactly the kind of coupling that produces
god objects.

The project crate's responsibility ends at "persist what the caller
hands me, atomically, with the source-hash bookkeeping." The caller
(M4.2 Tauri layer for UI flows, M4.8 batch runner for MT flows) owns
the decision of *which* status to write. This split matches the
existing pattern: the gate decides verdicts, the backend produces
targets, the project crate stores results.
